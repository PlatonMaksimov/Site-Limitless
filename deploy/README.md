# Развёртывание Limitless

## Состояние

Сайт, API формы и Telegram-бот находятся в одном репозитории. Backend —
один Node.js-процесс (HTTP API + polling worker), Nginx отдаёт только `dist/`.
Заявки и очередь уведомлений хранятся в SQLite. Зависимостей npm нет.
Требуется Node.js **22.16+** с `node:sqlite`; рекомендуется Node.js 24 LTS.

Это инструкция и шаблоны, а не свидетельство уже выполненного развёртывания.

## Вариант через MobaXterm

На Windows можно выполнить инструкцию без веб-терминала Aeza:

1. Установите MobaXterm с официального сайта.
2. Выберите **Session → SSH**.
3. Укажите IP сервера, порт `22`, пользователя `root`.
4. Введите пароль в поле запроса MobaXterm. Не сохраняйте пароль в сессии.
5. В левом SFTP-окне откройте `/opt/limitless` и используйте терминал
   справа для команд ниже.

Для команд, которые создают многострочные файлы, используйте `nano`:

```sh
nano /etc/limitless/limitless.env
```

Вставка в терминал MobaXterm обычно выполняется правой кнопкой мыши.
Перед вставкой убедитесь, что открыта нужная сессия сервера. Токены,
пароли и `.env` не загружайте через SFTP в Git-каталог.

Если SSH в MobaXterm зависает до запроса пароля, проверьте в консоли Aeza:

```sh
ss -lntp | grep ':22'
timeout 5 bash -c 'head -n 1 </dev/tcp/127.0.0.1/22'
journalctl -u ssh -n 30 --no-pager
```

Ожидается строка `SSH-2.0-OpenSSH...`. Если локальная консоль отвечает,
а MobaXterm нет, временно отключите VPN/прокси или добавьте IP VPS
в список прямого подключения. Не отключайте firewall и не переустанавливайте
SSH вслепую.

## Безопасность перед началом

- Заменить опубликованные в переписке пароль VPS и токен бота.
  Не записывать новые значения в Git, команды с журналированием или frontend.
- Проверить сервер через консоль провайдера: ОС, свободное место, открытые порты,
  другие сайты, Docker и существующие конфигурации. Не переустанавливать VPS.
- Настроить вход по SSH-ключу. Отключать пароль/root-вход только после проверки
  второго рабочего SSH-сеанса и доступа к консоли провайдера.
- Не включать реальный приём персональных данных по HTTP.
- Для включения формы нужен предоставленный владельцем настоящий документ,
  его версия и собственный числовой Telegram ID владельца.

## Структура на сервере

```text
/opt/limitless/releases/<release>/   код + dist (root-owned, читается сервисом)
/opt/limitless/current              симлинк на текущий release
/etc/limitless/limitless.env         секреты (root:root, 0600)
/var/lib/limitless/limitless.sqlite  данные (limitless:limitless, 0700 каталог)
```

`deploy/limitless.service` запускает backend от непривилегированного пользователя.
База хранится вне релизов и не перезаписывается при обновлении.
Не запускать одновременно два worker-процесса с одним токеном.

## Переменные окружения

На сервере создать приватный `/etc/limitless/limitless.env` по `.env.example`.
Его читает systemd; не копировать в `dist/`. Для HTTP-просмотра:

```dotenv
PORT=4180
SITE_ORIGIN=http://45.152.198.96
DATABASE_PATH=/var/lib/limitless/limitless.sqlite
TELEGRAM_BOT_TOKEN=<секрет, заполнить только на сервере>
TELEGRAM_OWNER_ID=<ваш числовой Telegram ID>
PRIVACY_URL=
PRIVACY_VERSION=
LEADS_ENABLED=false
TRUST_PROXY=true
RETENTION_DAYS=30
```

В таком режиме сайт доступен для просмотра, бот работает, но поля формы
заблокированы: без TLS нельзя безопасно принимать контактные данные.
Не устанавливать `SITE_ORIGIN=https://...` до фактической настройки TLS.

После настройки HTTPS и предоставления документа:

```dotenv
SITE_ORIGIN=https://ваш-домен
PRIVACY_URL=/privacy.pdf
PRIVACY_VERSION=<версия предоставленного документа>
LEADS_ENABLED=true
```

Документ разместить в `public/`, повторить сборку. Настроить Nginx на
HTTPS-сертификат, автоматическое продление и редирект HTTP → HTTPS.
Домен можно добавить позже: polling-боту входящий webhook не нужен.
HTTPS по IP возможен только с сертификатом, доверенным браузером;
самоподписанный сертификат не подходит для публичной формы/Mini App.

### HTTPS на IP до покупки домена

Let’s Encrypt поддерживает IP-сертификаты профиля `shortlived` (срок 160 часов).
Проверить поддержку установленного Certbot: `certbot --help all` должен
содержать `--ip-address` и `--required-profile`. Не устанавливать наугад
старый пакет, в котором этих параметров нет.

После доступности HTTP-01 challenge снаружи и согласования регистрации ACME:

```sh
certbot certonly --webroot -w /var/www/letsencrypt \
  --ip-address 45.152.198.96 --required-profile shortlived \
  --cert-name limitless-ip
```

Это образец будущей команды, она не выполнена. Сначала отладить получение
на staging CA; staging-сертификат браузеры не считают доверенным. Затем
выпустить production-сертификат, включить `nginx-https.conf` вместо HTTP-шаблона
и проверить `nginx -t`. Убедиться, что работает timer автоматического
продления, выполнить `certbot renew --dry-run`, настроить deploy-hook
`nginx -t && systemctl reload nginx` и мониторинг срока сертификата.
При таком коротком сроке ручное продление не подходит.

Официальные источники для проверки параметров перед установкой:

```text
https://letsencrypt.org/2026/01/15/6day-and-ip-general-availability/
https://eff-certbot.readthedocs.io/en/stable/using.html
```

Перезапуск после изменений: `systemctl restart limitless`.
Проверка: `systemctl status limitless`, `journalctl -u limitless -n 50`
(не публиковать конфигурацию и секреты).

## Установка и обновление

1. Проверить изменения, запустить `npm test` и `npm run build`.
2. Загрузить в новый release: `backend/`, `src/lead.js`, `package.json`, `dist/`.
   Не переносить `.env`, `.git`, `artifacts/` или локальную базу.
3. Создать пользователя `limitless` без shell, установить unit-файл,
   сохранить резервные копии существующих конфигураций.
4. Проверить шаблон `nginx-http.conf` и добавить отдельный virtual host,
   не удаляя другие сайты. Проверить `nginx -t` перед reload.
5. Переключить `current` на новый release, перезапустить backend,
   проверить health и сайт. Для отката вернуть предыдущий симлинк.
6. Не включать firewall вслепую: сначала сохранить доступ по фактическому
   SSH-порту, а также HTTP/HTTPS. Backend 4180 слушает только loopback.

## Быстрый порядок команд

Ниже минимальная последовательность после входа в MobaXterm/SSH:

```sh
apt update && apt install -y git nginx curl ca-certificates
mkdir -p /opt/limitless/releases
cd /opt/limitless/releases
git clone https://github.com/PlatonMaksimov/Site-Limitless.git 1.1.0
ln -sfn /opt/limitless/releases/1.1.0 /opt/limitless/current
cd /opt/limitless/current
npm test
npm run build
```

Затем выполните шаги создания пользователя, `.env`, systemd и Nginx
из разделов ниже. Не вставляйте токен Telegram в командную строку:
он может попасть в историю shell.

## Админка Telegram

- `/start` или `/id` — показывает только ID самого отправителя, не даёт доступа.
- `TELEGRAM_OWNER_ID` назначается оператором сервера; принцип «первый вошедший —
  админ» не используется.
- Владелец запускает бота и открывает `/admin`.
- `/add_admin 123456789` и `/remove_admin 123456789` — только владелец.
  Новый администратор должен сам запустить бота, иначе Telegram не разрешит
  боту первым начать личную переписку.
- Администраторы получают заявки; в панели можно управлять уведомлениями,
  смотреть статус и последние заявки.
- `/test` — тестовое уведомление только вызвавшему его администратору.
- Управление и заявки доступны только в личном чате с ботом. При отзыве
  доступа старые кнопки админки также перестают работать.
- Если уже настроен webhook, worker не удаляет его автоматически:
  сначала необходимо явно согласовать перенос существующего бота.

## Приём и доставка заявок

`POST /api/leads`: JSON `name`, `contact`, `service`, `message`, `consent: true`.
Услуги: `website`, `ads`, `both`, `unsure`. Обязательные заголовки:
`Content-Type: application/json`, корректный `Origin`, `Idempotency-Key: <UUID v4>`.

Backend проверяет данные, лимит размера 16 КиБ, источник, частоту обращений
и готовность обработки. IP используется в памяти только в виде хэша с
случайной солью; тексты заявок и токены в журнал не пишутся.

`{"ok": true, "id": "..."}` возвращается **после фиксации заявки и уведомлений
в базе**, а не до отправки сетевого запроса. Это подтверждение принятия
сервером, не обещание мгновенной доставки в Telegram. Worker повторяет
доставку при временных сбоях. Повтор HTTP-запроса с тем же ключом не создаёт
новую заявку. Telegram может доставить уведомление дважды при обрыве после
отправки до подтверждения; ID заявки позволяет распознать такой повтор.

Если все администраторы выключили уведомления, форма временно недоступна.
По умолчанию персональные данные удаляются из локальной базы через 30 дней.
Удаление из SQLite **не удаляет** уже доставленные сообщения в Telegram:
настройте автоудаление в чате и правила хранения самостоятельно.

## Резервные копии

Копировать SQLite штатным backup API/командой `.backup`, не простым копированием
активного файла при WAL. Бэкапы содержат персональные данные: ограничить доступ,
шифровать внешнее хранение и определить срок удаления. Не хранить их в Git
и публичном web-root. Откат кода не должен откатывать базу с новыми заявками.

## Проверки

`npm test` — server-side валидация, идемпотентность, origin/rate limit, запрет
отправки без HTTPS/документа/админа, сохранение и Telegram-авторизация.
Браузерная проверка: `node scripts/browser-check.mjs` с локальным Playwright.
На сервере дополнительно проверить TLS, перезапуск сервиса, заявку в Telegram
с синтетическими данными и сохранение очереди после рестарта.
